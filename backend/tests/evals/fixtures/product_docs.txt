AI 智能知识库 Agent 平台是一套面向企业内部文档的问答系统。它把用户上传的私有文档转换成可检索的知识库，再让大语言模型基于检索到的资料回答问题，而不是依赖模型自身的训练知识。平台的定位是一个可以直接运行、可以直接部署的完整系统，包含前端界面、后端接口、关系型数据库、向量数据库、模型服务以及容器化编排，而不是一个只跑在笔记本里的演示程序。系统目前只支持 TXT 格式的文档，并且要求文档使用 UTF-8 编码，用记事本保存的 GBK 编码中文文档会被拒绝入库，需要先转码后再上传。

平台的向量存储使用 Milvus。Milvus 是一个开源的向量数据库，专门用于存储和检索高维向量。系统把每个文档切片转换成 1024 维的向量后写入 Milvus 的 knowledge_chunks 集合，检索时按余弦相似度找出最接近的若干条切片。检索时必须带上 knowledge_base_id 过滤条件，否则会在全部知识库范围内做最近邻搜索，既会把别的知识库的内容返回给当前用户造成数据泄漏，也会让无关内容挤占返回条数的名额。

平台的业务数据存储在 PostgreSQL 中，包括知识库、文档、会话和消息四类数据。PostgreSQL 保存的是业务事实，可以参与事务和关联查询；Milvus 保存的是向量索引，擅长近似最近邻检索但不支持事务。两者之间没有分布式事务，跨存储的写入与删除无法原子完成，因此系统固定了操作顺序来降低不一致的风险：删除时先清理 Milvus，成功之后才删除 PostgreSQL 记录。如果 Milvus 清理失败就中止整个删除并返回错误，PostgreSQL 记录保持不动，调用方可以重试。

平台的回答生成使用 DeepSeek。DeepSeek 提供的是 OpenAI 兼容接口，请求体和响应结构与 OpenAI 一致，因此项目直接复用 OpenAI 官方 SDK，只把接口地址指向 DeepSeek 的服务端点。调用模型时使用异步客户端，因为一次生成往往要等好几秒，同步客户端会把整个事件循环堵死，导致其他请求只能排队等待。

文本向量化没有使用 DeepSeek，而是使用硅基流动托管的 BAAI/bge-m3 模型。原因是 DeepSeek 官方接口只提供生成模型，没有 embedding 接口，调用向量化接口会返回 404。因此 RAG 的两半由两家服务分别承担：把文本转换成向量用硅基流动，根据检索结果生成答案用 DeepSeek。bge-m3 输出的向量维度是 1024 维，这个维度必须在配置中显式声明，因为 Milvus 集合的维度在创建时就固定了，建好之后无法修改，改维度只能重建集合并把全部文档重新向量化一遍。

平台通过 MCP 协议接入外部工具。MCP 是 Model Context Protocol 的缩写，它把工具的实现和调用方解耦，工具可以更换实现、更换语言，甚至换成远程服务，而调用方不需要修改代码。当前的 MCP 客户端与 MCP 服务端之间使用标准输入输出通信，服务端由客户端作为子进程拉起，不占用端口也不需要单独部署。目前 MCP 服务端只提供一个工具，用于查询指定时区的当前时间，支持上海、东京和 UTC 三个时区。

RAG 的写入链路是上传文档时完成的，依次经过解析、切分、向量化和写入四个步骤。切分环节按语义边界断开，优先在段落和句号处切分，找不到才硬切，每个切片的长度上限是 500 个字符，相邻切片之间保留 50 个字符的重叠。保留重叠是为了防止一个完整的语义单元正好横跨切分点。向量化环节分批进行，每批最多 32 条切片，批量调用可以把多次网络往返合并成一次，明显降低入库耗时。

平台通过 Docker Compose 一键部署，一共编排了七个服务，包括前端、后端、PostgreSQL、Milvus 以及 Milvus 依赖的 etcd 和 MinIO，还有一个一次性的卷属主初始化任务。启动顺序由健康检查控制，PostgreSQL 与 Milvus 就绪之后后端才启动，后端就绪之后前端才启动。后端在启动时会依次执行数据库迁移、创建 Milvus 集合、启动服务，任何一步失败都会中止启动，避免服务在集合不存在的状态下运行。所有数据都保存在 Docker 命名卷中，执行停止命令不会删除它们，需要显式加上删除卷的参数才会清理。

多轮对话依靠会话编号串联上下文。每次请求都要带上上一轮返回的会话编号，服务端据此读取该会话最近的若干条历史消息，连同本轮问题一起交给模型，模型才能理解「它」「这个」这类指代。历史消息按条数限制而不是按长度限制，每次最多取最近 10 条。会话的归属校验只依据数据库中的知识库字段，不使用任何内存状态或缓存，因为缓存在重启和多实例部署下都会失效，会让用户换个实例提问就被判定为无权访问。

平台的 Agent 与固定检索问答的区别在于「要不要检索」的判断权。固定问答每次都先检索再作答，而 Agent 先把问题交给模型，由模型自己决定需不需要查资料、用什么关键词查。查询完成后把结果交回模型让它继续推理，直到模型给出最终回答。这样做的收益是寒暄类问题不会被硬塞进一堆无关的检索结果。工具调用的往返轮数上限是 5 轮，用满之后会强制收敛为直接作答，避免模型陷入反复检索的循环。

Agent 的工具调用带有多重安全边界。首先是一份工具白名单，只有名单内的工具才允许执行，模型臆造的工具名会被直接拒绝。其次是参数收敛，模型请求的返回条数如果超过上限，会被收敛到上限值而不是报错。第三是知识库隔离，知识库编号由服务端从请求路径中取得，刻意不出现在工具的参数字段里，因此模型没有任何途径去检索别的知识库，即使被提示词注入诱导也无法越权。工具执行失败不会中断整个问答，错误会作为工具结果返回给模型，让它有机会换个说法重试或者基于已有信息作答。

平台内置了一套轻量的运行记录，用于回答「这一轮慢在哪、卡在哪」。它记录每次模型调用和每次工具调用的耗时与成败，以及整个请求的总耗时和循环轮数。运行记录只在当前请求的生命周期内存在，不写入数据库。出于安全考虑，它不记录接口密钥，也不记录完整的提示词或消息内容。模型启动的工具调用如果被白名单拒绝，同样会留下一条失败记录，因为「模型反复请求一个不存在的工具」恰恰是排查 Agent 行为时最需要的线索。

知识库检索接口的返回条数范围是 1 到 20，默认返回 5 条。这个上限的存在是为了控制成本：返回条数越多，拼进提示词的资料就越长，token 消耗和响应延迟都会随之上升。而 Agent 内部调用检索工具时，允许的返回条数范围更紧，上限只有 5 条，因为这里的条数由模型决定而不是由用户决定，模型没有节省成本的动机，给一个宽松的上限它就可能每次都取满。
